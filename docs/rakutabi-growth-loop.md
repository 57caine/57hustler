# 楽旅くん：数値を見ながら改善する運用
更新日：2026-10-29（JST）

## オーナー方針と承認範囲
旅行系の過去の楽天アフィリエイト成果を踏まえ、楽旅くんの使い勝手と送客を最優先、次にレンズナビ。過去の楽天全体の売上は楽旅くんへの帰属・確定報酬の証明ではない。
オーナーは「サイトの使い勝手を数値を見ながら勝手に改善まで回す」運用を依頼した。根拠のある小さく可逆な表示・案内文・サイト内導線・アクセシビリティは、必要な検証と対象CIを通したPRを残し、マージ・既存公開処理・本番全対象確認まで進めてよい。
外部送客先、アフィリエイトURL、価格算式、計測の意味・収集範囲、認証、権限、決済、投稿、noindex、新規課金、大きな挙動変更は対象外。別途具体的な承認を必要とする。

## 一回の手順
1. main・AGENTS.md・CLAUDE.md・この文書・直近PR/Actions・前回結果を読む。開いている楽旅PRの続きを優先し重複作業を作らない。
2. /statsを公開URLから直接取得する。Vercel接続の403だけで未取得としない。取得日時・期間・証拠URLを記録する。
3. /statsの日別行から昨日までの7日と前7日を集計。当日込みのカードと区別する。GA4は処理遅延を踏まえ取得できる確定期間を明示し、同じ期間・定義だけを比較する。
4. 訪問 → 条件・テーマ・宿への内部遷移 → 楽天送客 → 楽天側の予約・確定報酬を区別。取得できない段階は未取得、取得結果0は0。閲覧分母がない場合は送客率を算出しない。測定IDだけからGA4閲覧権限があるとは判断しない。
5. スマホで「探す→条件を選ぶ→宿を比べる→楽天へ進む」の導線を確認。検証用にアフィリエイトリンクを実クリックして成果を汚さない。少数データしかないときは計測確認と再現する不具合の修正を優先し、売上増減を断定しない。
6. 一回最大一件。基準値、問題の証拠、仮説、評価指標、対象ファイル、検証、戻し方をPRへ記録。根拠がなければ変更を増やさず不足を記録する。
7. 必要なテストと対象CI合格を確認。独立レビューがなければ未実施と記す。継続承認内の小さな変更だけ既存公開処理まで進め、対象ページを全件fetchし公開内容を確認。CI待ち・公開失敗なら次回はそのPRを優先。
8. 公開後は最低7日の確定期間を観察（定着・件数不足なら延長）。同じ導線に別の数値改善を重ねない。安全上の不具合修正は例外として記録する。比較できても因果を断定しない。効果不明は不明と残す。
