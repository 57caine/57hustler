# データ取得（自動化）の調査結果と方針

## わかったこと（WebSearchベース、未検証）
- 楽天お買い物マラソンは「開催予告が開催の約2日前・10時に楽天市場TOPページで行われる」という情報が複数の第三者メディアに記載されている
- 開催頻度は12月を除き月1〜3回程度。年間スケジュールは楽天から事前に公式発表されていない
- `calendar.rakuten.co.jp` という「楽天カレンダー」ページ、および TimeTree 上の「楽天市場キャンペーンカレンダー（公式表記あり）」が存在することが検索で確認できた。これらが本当に楽天公式が運営するものか、ICS/RSS/API等の構造化データを配信しているかは**このセッションでは未確認**

## 確認できなかったこと（重要）
- このセッションの実行環境はネットワークアウトバウンドが組織ポリシーで制限されており、`rakuten.co.jp` 系ドメインだけでなく `example.com` 等の一般サイトへの直接fetchも `EGRESS_BLOCKED` で失敗した
- そのため、`event.rakuten.co.jp` や `calendar.rakuten.co.jp` の実際のHTML構造・DOM・APIエンドポイントを**実地確認できていない**
- 「確認できていません」という前提のまま、未検証のセレクタでスクレイパーを実装することはリスクが高いため、今回はスクレイパー本体（Playwright実装）はまだ書いていない

## 次にやるべき検証（1回だけの判断）
1. 実際にネットアクセス可能な環境（オーナーのブラウザ、またはGitHub Actions上のワンショットジョブ）で以下を目視確認する
   - `event.rakuten.co.jp` 配下の「お買い物マラソン」「スーパーセール」特設ページのURLとHTML構造
   - `calendar.rakuten.co.jp` が本当に楽天公式か、構造化データ（ICS/RSS/API）を配信しているか
2. 確認結果をもとに、`scripts/update-prices.ts` と同じ設計思想（Playwright + セレクタ探索 + 取得失敗時は既存データ保持 + 異常値検知）でスクレイパーを実装する
3. GitHub Actionsで1日数回自動実行し、`data/campaigns.json` を自動更新する体制にする（`.github/workflows/update-prices.yml` と同様の構成を想定）

この検証が終わるまでは「エントリー期間を自動取得して表示」ではなく「手入力データで表示」という状態であることを、他の作業者にも申し送りする。
