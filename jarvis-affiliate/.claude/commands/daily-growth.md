# /daily-growth — 日次グロースループ

追加の切り口：$ARGUMENTS

所要の目安は10分。**投稿・LP改修の実行はせず、提案と下書きまで**（実行はオーナー判断）。

## 1. 健康診断

```bash
npm run validate
```
エラーがあれば、集客より先にそれを報告する（壊れたLPに人を集めない）。

## 2. 数値を見る

1. #207の既存監査・台帳と同一期間/媒体/案件のデータを再利用する。監査・実験・監視・スケジュールを複製しない
2. 実データが揃う場合だけ `npm run metrics -- --no-sample` を参考出力として読む。現行metricsは欠測0化・案件共有時の二重計上等が未修正のため、確定報酬・採算の合格証拠には使わない
3. データがなければ「未取得」と理由を記録。デモへの自動切替をしない。明示demoモードの出力は実データ判定と分離し、承認・ゲート合格を生成しない
4. `JARVIS-2.0-SPEC.md` §2に従い、原本の空欄/欠落と0を区別。不正数値、期間/TZ/媒体/コホート不一致、重複排除不能を検出したら集計・診断を止める
5. GA4 sessions/クリックイベントとASPクリック/発生/保留/確定/否認/取消を別列表示。汎用報酬額を確定と扱わず、帰属不能はunattributedに一度だけ計上。LP別利益/EPC/RPSは未算出
6. 同期間の前回値と比較し、出典・取得日時・観測分母・欠測・限界を3行で要約。クリック増を成約率/利益/因果実証にしない

## 3. 改善案を1つに絞る

- #207配下の最大1実験に統合し、欠測があればその解消を最優先の1件とする。データが揃う場合は事前仮説・採否基準・停止条件・観測期間・費用上限0・戻し方を付けた1件を提案
- 対象の `content/campaigns/{slug}.md` について、変更前／変更後の差分案を示す（まだ書き換えない）
- 同じLPで前回の改善を試している途中なら、新しい改善は出さず「計測継続」とする（1度に1つだけ変える）

## 4. トレンド切り口を更新する

- 今回の#209では設定を書き換えず、必要なトレンド切り口は提案に留める。既存SNSの投稿内容・頻度・方式・停止設定は変更しない
- 引数で切り口が渡されていれば `--trends` に使う
- 根拠のない「流行っている」主張は書かない。時期の事実（年末・新年度など）に基づく切り口にする

## 5. SNS投稿案を作る（公開ではなく下書きのみ）

```bash
npm run social                       # 引数ありなら: npm run social -- --trends "$ARGUMENTS"
```
- `output/social/{日付}/*.md` を読み、各LPから X・Threads それぞれ上位3案を選ぶ
- 全投稿に `#PR` があること、NGワードがないこと、リンクがLP（UTM付き）であることを確認
- 必要なら言い回しを自然に直す（数値・事実は変えない）

## 6. 報告（この形式で）

1. **今日の状態**：エラー有無／主要数値の変化（3行）
2. **おすすめ改善1件**：対象LP・変更前後・期待する効果・測り方
3. **投稿案**：必要な場合だけ、PR表記付きの未公開下書き。今回の文書反映では投稿案生成も未実施
4. **判断してほしいこと**：改善を実施するか／投稿するか／提携申請が必要な案件
